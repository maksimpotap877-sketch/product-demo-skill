# Installation and launcher

The canonical Skill ships in the toolkit package. `skill install --scope user --client codex` copies it to `.agents/skills/product-demo`; `--client claude` uses `.claude/skills/product-demo`. Both are under the current user's home. Claude's user path respects `CLAUDE_CONFIG_DIR` when configured. `--scope project --project <path>` places the selected client directory inside that project. `--client both` creates the two client copies while sharing one runtime. The default client is `codex`.

Installation creates an allowlisted local `.tgz`, installs a content-versioned runtime under the user's application-data directory and writes `install.json`. No administrative symlink or unpublished `npx` package is required. The launcher is client-neutral; choosing GLM in Claude Code uses the Claude path. There is no GLM-specific Skill directory.

On Windows the manifest is normally `%LOCALAPPDATA%/product-demo-toolkit/install.json`; the launcher resolves the runtime there rather than in the current working directory. Installation records the manifest's physical path in the owned `.runtime-location.json` file, including Windows app-container redirection when applicable. `PRODUCT_DEMO_DATA_DIR` can explicitly choose another data root. `node <skill-dir>/scripts/run.mjs --runtime-path` prints the installed package root, useful for a trusted config import. Do not use the original development repository's absolute paths in other projects.

`skill status --client codex|claude|both --json` reports installed paths, runtime availability and user modifications (choose one literal client value). Reinstallation preserves modified owned Skill files under the app-data `backups` directory before replacement. An unowned Skill is not overwritten. Conflicting user/project copies for the same client are rejected. Separate Codex and Claude copies are intentional. Clients that read both directories, such as OpenCode, should use only one copy and verify discovery.

`skill uninstall --client claude` moves that owned Skill to a backup, removing its discovery while preserving the Codex copy. Select `both` to remove both client copies. Use the same scope/project options as installation. Runtime versions, generated videos, profiles, voice caches/models, integrations and backups remain untouched. Their deletion is a separate explicit user operation. Never remove an unowned Skill just because the folder name matches.

The package manifest lists every included file. Only runtime, render source, built-in examples, Skill resources, voice helper scripts and selected documentation are accepted. Outputs, auth, browser profiles, `.env`, archives and user media are rejected. Installed dependencies are local to the versioned runtime; they are not reinstalled for each CLI command.

Neural speech uses its separate pinned Python environment and voice cache under application data; the first requested neural preview/narration can create it on another host with Python and network access. External text authorization is per task scope, not inherited merely by copying a config. Remotion MCP and the official `remotion-docs` Skill are separate user integrations, documented in [remotion.md](remotion.md); product-demo installation and uninstall must not overwrite or remove them. The toolkit's local renderer does not require the documentation MCP to be online.

Refresh or start a new client session if its Skill list is stale. Invoke `$product-demo` in Codex or `/product-demo` in Claude Code. Merely placing a file in the folder is not proof of client discovery; verify the actual client's Skill listing when testing an installation. Do not claim an authenticated Claude/GLM end-to-end run from launcher tests alone. On another computer, install from the release/source again rather than copying this host's runtime pointer.
